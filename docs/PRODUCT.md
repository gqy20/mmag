# MMAG 产品定义

- 状态：Draft
- 日期：2026-08-14
- 范围：Mattermost 中的统一智能工作助手、协作空间、记忆边界与任务执行体验

本文从用户问题和产品体验定义 MMAG，不替代 Agent Package、Capability、Policy、Scope 或 Runtime
技术契约。文中“当前基线”仅描述已经实现的能力；“目标体验”和“产品要求”是后续产品与工程验收依据，
不表示代码已经全部支持。

## 1. 产品定位

MMAG 是运行在 Mattermost 中的企业智能工作助手。用户通过一个统一入口表达目标，MMAG 负责理解、澄清、
调用合适的专业能力并返回真实、可追溯的结果。

用户不需要了解 `core_agent`、Project Agent、Skill、Tool 或 Capability，也不应该通过试错判断某个内部
Agent 是否拥有某项工具。内部智能体分工是实现细节，不是用户操作模型。

一句话产品承诺：

> 在用户已经工作的对话中，用自然语言安全地完成工作，而不是让用户学习一套智能体组织结构。

## 2. 用户核心问题

MMAG 优先解决以下问题：

1. 用户知道要完成什么，但不知道应该找哪个 Agent、使用哪个 Tool 或采用什么格式；
2. 工作上下文分散在私聊、频道、Thread、项目资料和历史结果中，重复说明成本高；
3. 聊天回答与真实业务动作脱节，用户无法确认任务是否真的创建、文件是否真的交付；
4. 个人信息和群聊信息边界模糊，用户不知道系统记住了什么、会在哪里使用；
5. 文档、会议、目标和任务分散在多个协作界面中，信息已经被整理，却没有形成持续推进的工作闭环；
6. 自动化过程缺乏进度、权限、来源和失败解释，用户难以信任和纠正结果。

## 3. 目标用户与核心场景

### 3.1 普通成员

- 在 Bot 私聊中管理个人工作、偏好、长期记忆和个人 Skill；
- 在群聊中提问、总结讨论、提取待办或发起业务动作；
- 不需要理解内部路由，能够确认动作是否成功及其影响范围。

### 3.2 项目负责人和管理者

- 将群聊讨论转化为可跟踪任务、报告和 Artifact；
- 查看状态、来源、负责人和阻塞项；
- 对高风险动作进行批准、驳回或返工。

### 3.3 企业管理员和安全负责人

- 控制 Bot 安装、能力、模型、数据范围和保留策略；
- 审计谁在什么 Scope 执行了什么动作以及为何被允许；
- 在人员退出、频道权限变化或 Bot 停用时及时撤销访问。

## 4. 产品原则

### 4.1 一个入口，内部专业分工

默认向用户提供一个 MMAG 入口。Core Agent 只承担理解意图、必要澄清、协调执行和统一呈现，不直接拥有所有
领域能力。任务、报告、演示文稿等工作由专业 Agent 执行，但切换过程对用户透明。

### 4.2 先理解目标，再选择能力

系统首先判断用户想得到的业务结果，以及当前信息是否足够。只有在目标、Scope 或必要参数确实影响结果时
才追问；不得把“选择 Agent”“选择 Tool”作为普通用户的必答问题。

### 4.3 统一入口不等于共享数据

同一个 Bot 可以服务所有用户和频道，但个人、频道、项目、任务和运行状态必须分别隔离。数据能否使用由
当前真人、会话位置、业务 Scope 和实时权限共同决定，而不是由 Bot 身份或模型判断。

### 4.4 回答与执行必须真实

产生副作用的请求只有在业务系统确认成功后，才能向用户宣称“已创建”“已更新”或“已发送”。系统不能用
保存笔记、生成建议或自然语言承诺替代真实动作。

### 4.5 默认克制，风险显式

私聊可以保持连续对话；群聊默认只在明确触发时响应。涉及外发、删除、高风险写入或敏感资源时，应说明影响、
执行审批，并保留可审计结果。

## 5. 产品与身份模型

MMAG 将以下身份分开：

| 概念 | 用户可见含义 | 产品责任 |
|---|---|---|
| 真人用户（Actor） | 发起、修改或审批工作的人 | 权限与责任主体 |
| Surface Bot | Mattermost 中接收和发送消息的入口身份 | 安装、连接、展示和交付 |
| Core Agent | 用户目标的统一协调者 | 理解、澄清、路由和呈现 |
| 专业 Agent | 完成任务、报告、PPT 等专业工作的内部角色 | 领域推理与受控执行 |
| Persona | 经用户或组织发布的可选代理身份 | 明确代理边界和来源 |
| Scope | 当前数据与动作的有效范围 | 隔离、授权、检索和审计 |

Bot 数量不决定数据隔离，Agent 数量也不决定用户入口数量。

## 6. Bot 分层策略

### 6.1 默认方案

默认采用“一个租户安装一个统一 Bot”：

- 同一企业中的用户在私聊、频道和 Thread 中使用同一个 MMAG；
- 系统在内部为不同用户、频道、项目和运行构建独立上下文；
- 不按用户数量或群聊数量自动创建 Bot Account；
- 内部专业 Agent 不需要拥有独立 Mattermost Bot 身份。

### 6.2 可以增加真实 Bot 的条件

只有出现以下明确需求时才增加 Surface Bot：

- 不同企业租户需要独立安装、Token、品牌、策略或数据生命周期；
- 财务、法务、生产运维等安全域要求独立连接身份和管理员治理；
- 已正式发布的个人 Persona 或部门数字员工确实需要独立头像、`@mention`、消息历史或频道成员关系；
- 两个入口面向不同产品人群，用户预期和权限模型显著不同。

新增 Bot 不能改变 Actor、Scope、审批和审计规则，也不能成为跨 Scope 共享记忆的理由。

## 7. 会话与触发体验

### 7.1 Bot 私聊

- 用户消息默认视为发给 MMAG；
- 允许延续当前私聊上下文；
- 可以使用本人已授权的个人偏好、记忆和工作案例；
- 涉及团队资源时仍按用户当前权限访问，不能因为在私聊中就扩大权限。

### 7.2 频道与群聊

- `@MMAG`、回复 Bot 所在线程、Slash Command 或交互按钮属于明确触发；
- 普通频道消息默认不启动有副作用的执行；
- 主动总结或提醒只能由管理员显式开启，并说明触发范围与数据使用方式；
- 群聊只使用当前共享 Scope 允许的数据，不注入任何成员的私人记忆。

### 7.3 任务型请求

用户说“创建一个任务”“把这个整理成报告”等话语时，目标体验是：

1. MMAG 识别期望的业务结果；
2. 根据可信会话上下文确定 Actor 与 Scope；
3. 仅在缺少必要信息时追问；
4. 内部选择专业 Agent 和受允许能力；
5. 执行前完成权限、资源、审批和幂等检查；
6. 返回真实结果、关键字段和下一步，而不是暴露内部工具缺失。

如果当前入口不能安全执行，MMAG 应说明缺少的权限或触发条件，并给出用户可以完成的下一步。不得用
`save_knowledge` 等无关能力伪装任务已经落地。

## 8. 记忆与上下文产品模型

记忆属于用户、协作空间或业务对象，不属于某个 Agent。Agent 只接收当前请求被允许使用的上下文投影。

| 信息类型 | 建议范围 | 使用规则 |
|---|---|---|
| 当前对话上下文 | Conversation / Thread | 支持连续交流，受长度、时效和编辑删除影响 |
| 个人偏好与长期记忆 | Tenant + User | 默认只在本人私聊使用，跨 Scope 使用必须显式授权 |
| 频道知识与讨论 | Tenant + Channel | 仅当前有权访问的频道成员可用 |
| 项目知识 | Tenant + Project | 按项目成员和资源权限查询 |
| 任务、审批和 Artifact | 业务对象 Scope | 以正式业务状态为准，不降级为自然语言记忆 |
| Run 与 Checkpoint | Run / Thread | 仅用于恢复、审计和幂等，不作为用户画像 |

用户应逐步获得以下控制能力：

- 查看“MMAG 记住了什么”、来源和适用范围；
- 修改、停用或删除个人记忆；
- 把私人内容发布到团队空间时进行明确确认；
- 在源消息删除、离开频道或权限撤销后阻止后续访问；
- 区分聊天上下文、长期记忆和正式业务记录。

## 9. 统一工作对象与工具体系

MMAG 不为每种外部系统另建一套独立产品，也不把 Tool 直接等同于 Agent。Goal、Task、
Lark 文档、Lark Task 和联系人解析应复用同一套 Schema、Policy、审批、幂等、审计和错误契约。

### 9.1 正式工作对象

文档和会议记录是工作来源，不是 MMAG 需要重复建设的文档管理系统。MMAG 负责在用户提出目标时连接已有内容，
形成并持续推进正式工作对象：

```text
Document / Meeting / Conversation
  → SourceRef
  → Goal / Success Criterion / Decision / Task
  → Reminder / Progress Update / Artifact
```

- Goal 表达希望达成的结果，Success Criterion 可选地表达可验收条件；
- Task 表达具体行动，可以关联 Goal，也可以直接属于项目；
- Decision 表达已经确认的项目结论；
- Reminder 根据正式 Task 状态确定性调度；
- SourceRef 保留原始文档、会议、消息、版本和引用位置；
- Goal、Task、审批、提醒和 Artifact 都是正式业务状态，不存入自由文本记忆。

MMAG 不新增一套与当前 Task 平行的“会议 Todo 系统”。会议纪要或文档只能生成候选工作项；负责人、时间、
目标或影响不明确时，先由用户确认，再调用正式 Goal/Task 能力。

当前已实现本地团队知识与 Mattermost 消息检索的统一 `KnowledgeQuery/KnowledgeResult/SourceRef`，以及
会议行动项 → 人物候选 → 用户确认 → 正式 Task 的闭环。Lark 文档/会议 SourceRef、Goal 业务对象和
Reminder 调度仍是后续 Provider/业务状态能力，不能把本地契约写成已经接通外部系统。

### 9.2 简化目标系统（当前已实现）

用户所说的“OKR”当前指向从文档提取目标、行动项并持续跟进，不等同于飞书 OKR 产品或完整的
Objective/Key Result 管理套件。第一版作为模块化单体内 Product Workflow 的业务对象，不拆独立服务、
不新增独立 Agent：

| 对象 | 最小契约 |
|---|---|
| Goal | ID、标题、Scope、负责人、状态、可选起止时间、SourceRef |
| SuccessCriterion | Goal ID、可验收描述，可选当前值/目标值/单位 |
| Task link | 现有 Task 增加可选 `goal_id`，不复制任务状态 |

Goal 只使用 `draft → active → completed/cancelled` 生命周期。第一版不做组织层级对齐、权重、打分、
复杂周期和级联拆解。文档没有明确目标时直接生成候选 Task，不强制创建 Goal；模型只能提出候选目标和
验收条件，用户确认后才进入正式状态。

### 9.3 Capability Catalog 与执行 Provider

模型可见的是严格、稳定的业务 Capability，而不是任意 CLI：

```text
task.create
task.list
task.update
task.get_overview

lark.document.read
lark.document.search
lark.document.update
lark.document.get_revision
lark.contact.resolve
lark.task.create
lark.task.update
```

上述名称表达目标能力，最终实现时以项目 `CapabilitySpec` 命名规范和实际注册结果为准。每项能力必须定义严格
输入输出、READ/WRITE effect、permission、timeout、source policy 和错误语义。

`lark-cli` 只作为 Lark Capability 的一种底层 Provider/Handler 实现，不直接向模型暴露通用
`lark_cli(command)`、Shell 或自由命令字符串。Adapter 使用固定 argv 调用经过允许的操作，并把输出转换为
结构化结果；Lark 凭证留在控制面，不进入 Prompt、Agent/Skill Manifest、普通日志或 Artifact。

未来由 `lark-cli` 切换到 Lark OpenAPI SDK 时，上层 Capability、Agent 和产品交互契约不应随之改变。

### 9.4 Agent 与 Skill 的能力投影

Capability 在平台统一注册，不表示所有 Agent 都可见。运行时工具集合仍是 Agent allowlist、Skill 声明、
Package Policy 和请求级授权的交集：

| 执行角色 | 建议能力范围 |
|---|---|
| Core Agent | 意图协调、必要查询和严格 handoff，不持有全部 Lark/Task 写能力 |
| Project Agent | MMAG Goal/Task、负责人解析，以及经允许的 Lark Task 投影 |
| Report Agent | Lark 文档/妙记读取、来源化总结和候选行动项提取 |
| Reminder Service | Task 状态读取、提醒计划和 Outbox，不依赖模型定时唤醒 |

简化 Goal 由 Project Agent 处理，不单独注册 Goal Agent。只有未来出现独立组织治理、权限和周期边界时，
才重新评估拆分。

### 9.5 Lark 文档、知识与记忆

Lark 文档已经承担内容整理和协作，MMAG 默认只保存受控引用、版本、来源及必要索引，不复制成另一份长期记忆：

- 文档读取结果形成带 `document_id`、revision、ACL/Scope 和 SourceRef 的上下文快照；
- 文档普通修改只更新来源索引和版本，不自动改写个人记忆；
- 明确行动项生成候选 Task，结果目标生成候选 Goal/SuccessCriterion，项目结论生成候选 Decision；
- 稳定个人偏好只有经用户确认后才能进入个人记忆；
- 文档删除、权限撤销或来源失效后，相关上下文和派生知识必须停止使用并传播撤销状态。

### 9.6 本地 Task 与 Lark Task

第一阶段保持 MMAG Task 为统一内部工作对象，Lark Task 作为可选外部映射。每个映射至少保存 provider、
external ID、external revision、同步状态和稳定幂等键。

每个对象必须明确 authoritative source；在冲突策略、身份映射和版本检查完成前，不实现无约束双向同步。
MMAG 回复“已同步到 Lark”必须以外部写入真实成功为依据，不能把本地 Task 创建成功等同于外部同步成功。

### 9.7 统一用户链路

用户说“根据上周项目会议纪要整理研发待办并提醒负责人”时，目标链路是：

1. Core Agent 理解用户希望推进工作，而不是重复整理文档；
2. Context Service 根据可信身份和权限获取指定 Lark 文档或会议纪要；
3. Report/Project Agent 提取带 SourceRef 的候选 Task、负责人和时间；
4. 对不明确或高风险内容进行最少必要确认；
5. Project Agent 通过正式 Task Capability 创建任务，并按配置投影到 Lark Task；
6. Reminder Service 根据任务状态和用户通知偏好建立提醒；
7. MMAG 统一返回已创建、待确认、外部同步和提醒状态。

用户全程只面对一个 MMAG，不需要选择 Agent，也不需要知道底层使用了 `lark-cli`。

## 10. Core Agent 产品职责

Core Agent 应保持简单，但协调能力要稳定。

Core Agent 负责：

- 理解用户目标和完成标准；
- 识别信息缺口并进行最少必要澄清；
- 根据交互位置和意图协调专业 Agent；
- 聚合进度、来源、审批状态和最终结果；
- 用统一语言解释失败、权限限制和可行下一步。

Core Agent 不负责：

- 持有所有领域 Tool；
- 把自然语言记忆当成任务、审批或 Artifact 的事实来源；
- 自行决定可信 Actor、Scope 或资源权限；
- 用自由文本替代结构化 handoff；
- 向用户暴露内部 Agent 版本、Tool 缺失或路由实现细节，除非用户正在调试系统。

## 11. 结果与状态反馈

每个请求至少应让用户知道：

- 系统是否已经理解目标；
- 工作正在处理、等待信息、等待审批、已经完成还是失败；
- 真实产生了哪些任务、文件或外部动作；
- 结果属于哪个项目、频道或个人空间；
- 哪些内容来自消息、文档或外部来源；
- 失败时用户能采取什么操作。

内部错误可以记录 Agent、Skill、Capability 和执行细节；普通用户错误应按产品语言表达，例如“当前频道没有
创建项目任务的权限”，而不是“core_agent 当前无 create_task 类工具”。

## 12. 产品要求与优先级

### P0：统一入口可信完成任务

- 用户无需指定内部 Agent 即可发起已支持的核心工作；
- 高置信度意图通过确定性控制层选择专业 Agent，模型只处理必要的语义判断和澄清；
- 所有副作用通过统一 Capability 执行链，并返回结构化真实结果；
- Task 继续作为正式业务对象，不以文档摘要、候选行动项或记忆替代；
- 私聊与群聊上下文严格隔离；
- 失败信息对用户可理解，对开发者可追踪。

### P1：可控记忆与连续协作

- 用户可查看和管理个人记忆；
- 项目、频道和个人上下文按来源与权限构建；
- 以精确 Capability 只读接入 Lark 文档/会议来源，保留版本、Scope 和 SourceRef；
- 从文档提取候选 Goal/Task/Decision，经确认后写入正式业务对象；
- Agent handoff 只传递严格 Envelope、业务对象和 Artifact ref；
- 编辑、删除、成员退出和权限撤销能够传播到后续检索与执行。

### P2：按需多 Bot 与主动协作

- 管理员可为安全域或已发布 Persona 配置独立 Bot；
- 频道可显式开启受控的主动总结、提醒或工作流；
- 在确定 authoritative source、身份映射和冲突策略后，支持 Lark Task 受控写入与同步；
- 多 Bot 仍共用一致的 Scope、Policy、审计和业务状态模型。

## 13. 验收场景

### 场景 A：私聊创建个人任务

用户在 Bot DM 说“明天下午提醒我整理季度复盘”。MMAG 在必要时确认时间，创建真实任务并返回标题、时间、
归属和任务 ID。其他用户和群聊不能读取该任务。

### 场景 B：群聊创建项目任务

用户在项目频道 `@MMAG 把接口超时问题建成高优先级任务，负责人是小王`。MMAG 使用当前频道/项目 Scope
解析成员并创建任务；没有权限、成员不存在或项目不明确时给出可行动提示，不伪造成功结果。

### 场景 C：私人记忆不泄漏到群聊

同一用户先在 DM 中保存个人偏好，再在公共频道提问。群聊响应不得使用或暗示该私人偏好，除非用户通过明确
流程将其发布到共享 Scope。

### 场景 D：内部路由对用户透明

用户从统一入口请求任务、报告或 PPT。无论内部经过多少 Agent，用户看到的是连续的一次工作过程；内部 Agent
缺少 Tool 时系统应修正路由或说明业务限制，而不是让用户重新选择 Agent。

### 场景 E：权限变化后失败关闭

用户发起工作后退出私有频道。在审批恢复、Artifact 交付或重试前，系统重新校验成员关系并拒绝越权操作，
同时保留可审计的失败原因。

### 场景 F：Lark 文档形成工作闭环

用户要求根据指定 Lark 会议纪要整理待办。系统以当前用户权限读取文档，返回带来源的候选任务；用户确认后
创建 MMAG Task，并按配置投影到 Lark Task、建立提醒。文档读取成功、内部任务创建成功、外部同步成功和
提醒建立必须分别呈现，任何一步失败都不能伪装成完整成功。

## 14. 产品指标

第一阶段优先观察：

- 意图完成率：用户不指定 Agent 时，支持场景最终成功的比例；
- 澄清成本：每个成功请求需要的额外追问次数；
- 真实动作一致率：回复“已完成”与业务状态成功一致的比例，目标必须为 100%；
- 路由暴露率：普通用户看到 Agent/Tool 缺失等内部错误的比例；
- 权限安全率：跨用户、跨频道、跨租户和权限撤销后的越权访问次数，目标必须为 0；
- 可恢复率：等待审批、重启或可重试失败后能够继续完成的比例；
- 来源覆盖率：由文档、会议或消息形成的正式工作对象中，具有有效 SourceRef 的比例；
- 同步一致率：声明已同步的外部 Task 与外部真实状态一致的比例；
- 用户纠正率与重复表达率：衡量系统是否真正理解目标和复用合适上下文。

指标必须结合任务类型、触发方式和 Scope 分析，不能用回复数量或模型调用量代替用户价值。

## 15. 当前基线与缺口

截至本文日期，当前代码已经具备：

- 单一 Mattermost Bot 入口，以及 DM、频道和 Thread 消息链；
- 基于可信 Mattermost Actor、Installation、Tenant、个人/频道 Scope 的隔离；
- 默认 `mmchat` Agent 与专业 Agent/Skill/Capability 体系；
- Project Agent 独占任务 CRUD，并可通过受控 delegation 接收任务请求；
- Project Agent 通过受治理 MCP 窄口读取飞书文档和当前授权用户的任务，并可在人工
  审批后创建飞书任务或设置提醒；
- CapabilityExecutor、Policy、审批、Checkpoint、Outbox、Artifact 和结构化日志基础；
- 个人记忆、Personal Skill、WorkCase 与 Persona 的部分产品链路。

当前 Lark 基线仅包含上述四个精确 Capability 和 `lark-cli` Provider。简化 Goal 已实现 Scope
隔离的持久化、验收条件、单向生命周期、Task `goal_id` 关联和确定性进展摘要；
Mattermost/Lark 逐用户身份映射、MMAG Task 与 Lark Task 映射或双向同步，也尚未实现文档到
候选任务再到正式任务的显式多阶段 Workflow。

仍需作为独立实施需求验证和完善：

- 统一入口对任务、报告、PPT 等高频意图的稳定路由与最少澄清；
- 普通用户错误语言与内部调试信息的分层展示；
- 群聊普通消息、`@mention`、Thread 和主动模式的完整触发契约；
- 记忆查看、撤销、跨 Scope 发布和权限变更传播的完整体验；
- Lark 与 Mattermost 的可信用户映射、文档读取、SourceRef、外部 Task 映射和同步冲突策略；
- 基于正式 Task 状态的确定性提醒调度与免打扰策略；
- 产品指标埋点、用户反馈与端到端验收集。

具体实现状态以 [Roadmap](ROADMAP.md) 为准；身份与 Scope 的已接受架构边界见
[ADR-0010](adr/0010-mattermost-identity-scope-isolation.md)；Mattermost 后续交互规划见
[MM_UX](MM_UX.md)。

## 16. 当前不做

- 不要求用户学习或选择内部 Agent、Skill 和 Tool；
- 不按每个用户或每个群聊自动创建 Bot；
- 不允许统一 Bot 成为跨 Scope 读取数据的理由；
- 不用自然语言回答替代真实任务、审批、Artifact 或交付状态；
- 不让模型自行扩大权限、创建 Bot、声明身份或决定可信 Scope；
- 不向模型暴露通用 `lark-cli` 命令、Shell 或外部系统 Secret；
- 不把整份 Lark 文档复制成个人记忆，也不把候选行动项宣称为正式 Task；
- 不在 authoritative source、身份映射和冲突策略明确前实现任意双向同步；
- 不为追求“多 Agent”数量增加没有明确用户价值的内部角色。

## 17. 待产品验证的问题

以下问题需要通过真实用户任务和数据验证，不在本文中提前固化：

- 私聊中哪些请求可以直接执行，哪些需要显式确认；
- 不同频道是否需要不同的主动响应策略和管理员配置；
- 用户希望以何种方式查看、修改和撤销记忆；
- 任务创建时项目、负责人、截止时间缺失到什么程度才值得追问；
- MMAG Task 与 Lark Task 分别在哪些场景作为 authoritative source；
- Mattermost 用户与 Lark 用户采用用户绑定、企业目录映射还是其他可信关联方式；
- 文档变化产生候选 Goal/Task 时，哪些情况可以自动接受，哪些必须人工确认；
- 哪些 Persona 或部门角色确实需要独立 Bot 身份；
- 进度反馈采用 Reaction、Thread 更新还是 Ephemeral 时最不打扰用户。
